# 长任务整理频率优化

用户反馈长任务频繁显示「整理任务」。本轮针对整理触发、请求预算及运行中窗口进行优化。

## 已复现的问题

在修改前的 MuMu 安装包上，同一个严格思考协议的合成任务执行 8 次工具调用、9 次普通模型请求，却额外发起 6 次摘要请求；任务能够完成，但中间频繁整理。基线为 `build/context-frequency/baseline-eight-steps.txt`。

原因包括：每轮工具循环都检查 16,000 Token 阈值，保留的两组原生回传可能已经接近该阈值；整理后没有增长间隔；短会话按 16 轮触发；历史按保存记录估算，与实际发送的历史投影不同。不同协议还可能重复计算已经被原生块替代的内容，或者计算根本不会回传的思考文本。

## 当前策略

- 默认软预算改为约 24,000 Token，硬预算保持 32,000；普通短对话不按轮数强制整理。
- 整理时向约 12,000 Token 的目标选择较早记录，尽量为后续步骤留出空间。整理后至少增长约 4,000 Token 才再次触发软预算整理，接近 30,000 时仍优先处理压力。新一轮追问和运行中循环共用增长阈值。
- 直接使用实际请求投影规划窗口，包括系统指引、工具定义、当前用户锚点、工作区上下文和受保护的原生调用。
- 使用现有服务商序列化规则估算真正发送的字段。先去掉图片 Base64，再按帧计入；遍历解码后的 JSON 字符串，避免把传输层转义重复计入预算。原始工具返回本身包含的 JSON 文本仍正常计算。
- 根据回传体积保留最新 1–2 组完整原生调用；不拆开助手调用、工具返回、推理和不透明签名。其余原生片段只有在有源检查点提交后才被替换，原始数据库记录继续保留。
- 摘要互斥按会话处理，一个会话等待摘要不会阻塞另一个会话整理或准备请求。

触发预算仍是应用的启发式估算，不是模型标称窗口或精确分词。大块不可删减的当前指令、近期回传或有效摘要仍可能要求必要的整理；超出硬预算时继续明确停止，不带残缺上下文执行任务。

## 验证方法与结果

MuMu 0，Android 15，ADB 始终指定 `127.0.0.1:16384`；使用合成会话和本地 HTTP 模型，不调用真实服务商。

同一 8 步严格协议任务的前后对照：

| 指标 | 修改前 | 优化后 |
| --- | ---: | ---: |
| 工具调用 | 8 | 8 |
| 普通模型请求 | 9 | 9 |
| 摘要请求 | 6 | 2 |
| 缺失思考字段／协议拒绝 | 0 | 0 |
| 最终结果 | 完成 | 完成 |

新增 `LongTaskCompactionFrequencyDiagnosticTest`：28 次不同参数的只读历史查询，实际 Room 记录、真实 VM 与 Ktor 请求链；摘要后检查原生配对，最后回读最早证据。另有 23 轮短对话，验证没有仅因轮数而整理。聚合数据保存在应用外部文件目录 `context-frequency/result.json`，主机副本在 `build/context-frequency/`。

最终测试结果：

- 28 步压力任务：29 次普通模型请求、7 次摘要；28 组不同参数和返回记录全部保留，摘要后原生配对及早期证据回读通过。
- 23 轮短对话：仅 1 次回答请求，0 次摘要请求。
- 全量单元测试 433 项：432 通过、1 项既有环境用例跳过、零失败。
- MuMu 13 项设备回归通过：5 项严格／宽松协议及摘要修复，长任务频率、检查点、停止后接续、后台确认与手动接管、实际命令执行，以及前一轮文件、会话并行和中断恢复的 3 项综合回归。最终日志为 `device-final-regressions.log`（10 项）和 `device-reliability-final.log`（3 项）。
- Debug、AndroidTest 和 Release 构建成功，Release lint/R8 检查通过，日志 `final-build.log`。最终 Debug 已覆盖安装到 MuMu，SHA-256 为 `B16B40AFD27F1BC72E005E00BEABB72CA2EE932D43574B402AF5BD94EADA0CBC`。

单元测试覆盖：服务商实际回传字段、JSON 转义、图片大小、增长阈值、模型／服务商／会话隔离、短会话、窗口投影、原生调用分组、跨会话并发与取消保留记录。原有格式修复、截断修复、来源校验、硬预算和任务接续回归继续执行。

开发中遇到一次测试 JVM 原生内存分配失败；降低临时构建并发和 JVM 资源后重跑。未修改项目的永久 Gradle 配置。
