# DeepSeek 百万上下文适配计划

状态：实施与验证完成。全量单元测试 448 通过、1 项环境用例跳过，MuMu 11 项设备测试通过；正式包已在 MuMu 覆盖安装并冷启动验证。
代码基线：`d1ff3e8`；规划开始时工作区干净，规划阶段只新增本计划。实施记录见 [DeepSeek 上下文适配](deepseek-context-2026-10-26.md)。

## 目标与范围

让 Floryx 使用 DeepSeek 官方已确认的百万上下文模型时，按模型容量管理历史、预留输出和触发压缩；界面与真正发送请求使用同一份预算。

本轮聚焦会话上下文。沿用当前 Chat Completions 协议、工具调用和检查点机制，不扩展到 Responses API、搜索接口或其他供应商能力更新。其他供应商及未知模型继续使用现有 24,000/32,000 Token 规则。

## 已核实的依据

- [DeepSeek 模型与价格](https://api-docs.deepseek.com/zh-cn/quick_start/pricing/)（2026-10-26）：`deepseek-flash`、`deepseek-v4-pro` 的上下文为 1M。`deepseek-v4-flash`、`deepseek-v4-flash-vision-exp` 是仍可调用的 Flash 旧别名。
- [Chat Completions API](https://api-docs.deepseek.com/api/create-chat-completion/)：输入与生成输出共同占用上下文；`max_tokens` 最大 393,216。未设置时，非思考模式默认 8,192，思考模式默认 65,536，`reasoning_effort=max` 默认 131,072。
- `TaskContextManager.kt` 当前全局固定 `softTokens=24_000`、`hardTokens=32_000`；界面、摘要触发和发送前校验都使用它。生产依赖注入没有模型覆盖规则。
- 当前摘要批次 20,000 Token、每次超时 30 秒。选择归档边界先按最近 4 轮切，再进一步缩短，不能直接适合大窗口保留更多原文。
- `ContextBudget.kt` 按实际协议投影后以 UTF-8 字节启发式估算，不是精确分词器。`ChatViewModel.publishContextWindow()` 会在活动请求更新时反复完整估算。

## 确定的实现决策

### 1. 官方接口与模型识别

新增小型、集中管理的 DeepSeek 上下文配置解析器，输入为实际 `ProviderConfig` 与 `ChatRequest`。

- 仅在 URL 解析后的 scheme 为 HTTPS、host 精确等于 `api.deepseek.com`、使用当前支持的 Chat Completions 基础路径（空路径、`/v1` 或 `/beta`，允许尾斜杠）时启用。
- 模型明确列举：`deepseek-flash`、`deepseek-v4-pro`、`deepseek-v4-flash`、`deepseek-v4-flash-vision-exp`。别名用于能力识别，已有会话保存的模型字符串不需要改写。
- 自定义服务商只要实际使用符合条件的官方地址也能识别；不依赖服务商显示名称或预设 ID。第三方转发地址、路径内含 deepseek 的地址、未知/旧型号不推断为百万上下文。
- 新建 DeepSeek 预设首选 `deepseek-flash`，更新相关预设测试。现有模型菜单保留可用旧别名。

### 2. 一套预算用于显示、压缩和发送

把模型标称容量、输入硬预算、输出预留、压缩阈值拆成不同字段。解析结果至少包含 `modelWindowTokens`、`outputReserveTokens`、`safetyTokens`、`hardInputTokens`、`softInputTokens`、`targetInputTokens`、`minGrowthTokens` 和摘要配置。

DeepSeek 本地策略采用以下初值，均为应用策略，不冒充服务端精确分词或精确拒绝边界：

| 项目 | 规则 |
| --- | --- |
| 标称窗口 C | 1,000,000 Token；官方 API 页面只写 1M，本轮保守按十进制百万配置 |
| 输出预留 R | 用户明确设置的有效 `maxTokens`；未设置时按上述非思考/思考/Max 默认值解析 |
| 安全余量 S | 50,000 Token，即 C 的 5%；减少启发式估算误差风险，不保证估算绝不偏小 |
| 输入硬预算 H | C − R − S |
| 首次整理阈值 | floor(H × 0.85) |
| 整理后输入目标 | floor(H × 0.60)，包含摘要、系统提示、工具定义及受保护记录 |
| 整理后最小增长 | floor(H × 0.10) |
| 紧急整理阈值 | H − floor(最小增长 / 2)，增长等待不能越过该阈值 |

默认思考模式示例：R=65,536，H=884,464，首次整理约 751,794 Token，整理目标约 530,678 Token。界面中的 1M 是模型容量，H 才是本轮可用输入预算。

输出规则必须与实际序列化一致：

- 使用现有 `ThinkingSupport` 的启用/归一化结果决定默认输出，不按原始开关或无效 effort 猜测。
- 对命中的官方 DeepSeek 模型，将解析后的有效输出限制显式写入 `max_tokens`；摘要请求的 4,096/8,192 等显式值优先。
- 显式输出限制不在 1..393,216 时给出明确校验错误，不偷偷扩大或缩小用户设置。
- 压缩请求根据自身的非思考模式和输出配置计算预算，不借用主对话的输出预留。
- 所有路径复用解析器，避免网络层、UI 和上下文管理分别维护默认值。

### 3. 改造上下文管理与大窗口压缩

- `TaskContextManager` 每次按当前请求解析策略，覆盖 `contextWindow`、`shouldCompact`、`recordCompaction`、`retainedNativeStart`、`prepare` 和 `requireFits`。保留可注入的小预算用于边界测试。
- 增长水位除了会话、服务商地址、模型外，还绑定有效预算配置；改变思考模式或输出上限后旧水位不能推迟新预算下的必要整理。
- DeepSeek 的归档边界按 Token 目标选取，尽量保留更长的近期原文；最近 4 轮作为可容纳时的保护偏好，而不是最大保留轮数。当前用户锚点和受保护的原生工具调用优先。
- 运行中的助手调用、全部对应工具返回、所需推理字段保持完整配对。历史投影继续采用现有 DeepSeek 存储历史标记，避免缺失 `reasoning_content` 的 400 错误。
- DeepSeek 摘要单批完整请求输入预算初值为 128,000 Token；需计算摘要指令、已有检查点和本批记录后分批，且不能超过摘要请求自身的 H。单条大记录继续使用现有明确摘录策略。
- DeepSeek 摘要每次超时改为 120 秒，支持立即取消；原有格式、来源、完整性校验及最多三次尝试规则继续生效。其他服务商沿用原摘要配置。
- 摘要成功才推进检查点。失败或取消时保留原记录；请求仍超过 H 时停止本轮。服务端上下文拒绝应显示清楚，不通过自动重放工具操作重试。
- 已保存的有效检查点继续使用，后续按新窗口增长；不自动撤销过去的摘要或批量重建旧会话。

### 4. 估算与界面性能

- 估算继续基于实际协议投影，覆盖系统提示、工具定义、历史、当前原生推理及图片占用；显示明确标注“估算”。累计账户用量不能代替当前窗口占用。
- 将大请求估算放到后台，合并高频更新；缓存不变的请求前缀或复用请求修订对应的估算，避免每个流片段都序列化百万 Token 历史。
- 选择归档边界时避免每移动一条记录就完整重建所有历史；用累计估算定位候选边界，再对最终完整请求做校验。
- 任何异步估算结果都校验会话、运行 ID、模型、服务商及预算配置；停止、切换或重开后丢弃旧结果，延续现有取消隔离。
- 圆环百分比按当前输入占用 / H 计算。弹窗区分“模型上下文 1M”“本轮可用输入预算”“估算已用”和“输出预留”，用简短说明交代预留空间；需要同步中英文文案。
- 草稿估算、发送准备、工具续轮和重开会话显示应一致。未知模型显示“本地预算”，不要称为已确认的模型容量。
- 会话总窗口与单次附件/工具结果限制分别处理：审计现有截断点，验证多轮文本能实际累积超过 32k；本轮不扩大附件内联和工具结果持久化的单条限额。

## 执行顺序与验收

1. **策略与协议**：实现解析器和输出预留；测试四个支持名称、官方自定义配置、URL 误匹配、未知模型、第三方同名模型、三档默认输出、显式输出及无效值。断言预算使用的 R 与最终 wire `max_tokens` 一致，其他服务商行为保持原值。
2. **上下文与摘要**：接入全部管理路径；验证超过 32k 但低于新阈值的请求零摘要、阈值边界及输出配置变化立即生效、一次整理后具有增长空间、摘要批次符合预算、来源/配对完整、取消及失败保留记录。复用既有测试的可注入小阈值，另加入真实尺寸大文本案例。
3. **界面与性能**：验证后台估算与异步隔离，切换模型/服务商/思考模式/输出上限后分母更新；检查 1M 文案、中文/英文和已有窄屏布局。记录 100k、600k 及接近 H 的合成历史估算耗时和内存，确保完整估算不占用 UI 主线程且停止可响应。
4. **MuMu 实机链路**：按 AGENTS.md 确认 MuMu 实际 ADB serial，所有设备命令显式指定。实例停止时用安装好的 MuMuManager 启动并等待启动完成。使用 Floryx Dev、真实 Room/VM/Ktor 和本地严格模拟服务验证超过 32k、接近阈值、工具续轮、摘要后证据回读、停止续接及重开会话。测试通过依赖注入/HTTP 测试传输把已识别官方请求导向本地服务，生产识别不能为了测试放宽为任意 deepseek 名称。
5. **构建交付**：通过相关及必要的全量单元测试、上述 MuMu 回归、Debug/AndroidTest/Release 构建及 Release lint，覆盖安装验证后的 Debug，更新上下文文档和 CHANGELOG。记录实际测试范围和日志位置。

MuMu 上通过 Compose 点击、输入、热键等进行界面验收前，执行模型须按用户的 computer-use 规则发选项确认并等到明确允许；纯代码、构建、无 UI 交互的设备断言可先执行。规划阶段不操作设备。

以上默认验收使用合成数据和本地模型服务，不消耗真实账户额度。若执行阶段要追加真实 DeepSeek 验证，应将少量合成的 >32k 请求及预算说明给用户，取得相应授权后复用现有配置；密钥不导出。没有实际发过百万输入请求时，交付说明应区分“本地百万窗口机制通过验证”与“官方接口百万输入实测”。

完成标准：官方 DeepSeek 的显示、压缩触发、输出预留、最终请求校验都采用新策略；超过旧 32k 的真实设备请求成功通过本地完整链路；接近新预算时能整理并继续，工具证据与取消恢复不回归；其他模型保持原策略。
