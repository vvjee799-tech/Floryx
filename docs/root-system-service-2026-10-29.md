# Root 系统服务：第三批

目标为用户已授权的 iQOO Neo8 Pro / Android 16 / OriginOS 6，开发包为 `com.flowchat.app.debug`。本批将设备操作从应用进程内逐条执行 `su -c`，迁移到按需绑定的独立 Root 进程；不修改 BL、KernelSU、环境隐藏或系统默认助手设置。

## 接入与权限边界

- 使用 libsu 6.0.0 的普通绑定服务模式启动 `RootDeviceService`。启动时单独创建并验证 Root shell，发出启动任务后关闭该 shell，不使用全局缓存 shell、daemon 模式或开机自启。
- `IFlowChatRootService` 管理连接信息和独立请求，既有 `IFlowChatShizukuService` 继续承载设备操作。Shizuku 接入协议保持兼容。
- 连接核对真实服务 UID、PID 与协议版本；UID 不是 0 或协议不兼容时不发布能力。控制接口和每个操作 Binder 都校验原应用的完整 UID，不开放给其他应用。
- Root 进程内执行设备命令及已授权的托管命令时直接继承 Root 身份，不为每条命令再次启动 `su`。模型工具的权限、确认和命令执行开关仍由原调用链控制。
- 新依赖的仓库仅允许 libsu 分组；版本固定为 6.0.0，许可证随应用放在 `assets/licenses/libsu-LICENSE.txt`。

## 请求、取消与断线

每次调用分配独立 UUID 和命令执行器，结束后销毁该请求的执行资源。客户端最多并行执行 4 个请求，服务端最多保留 8 个请求。取消通过另一个 Binder 调用关闭对应执行器，而不是等待被阻塞的同步调用自行返回。

服务保留有界的取消记录，处理“取消先于 openRequest 到达”的时序。取消一个请求不关闭其他请求；正常结束启动命令的请求，也不会取消已转交托管命令注册表的任务。

Binder 死亡会清空连接验证和能力。下一次新操作可以重建连接，但失败或返回结果不明的原操作不会自动重放。Root 管理器拒绝后，被动刷新不会继续申请，需显式重试。新的连接重新获取 Root 身份；没有轮询管理器的授权文件，也不据文件可见性否定用户已完成的 Root。

## 子进程与资源生命周期

- 服务按操作复用，最后一个请求完成后启动 30 秒空闲计时；没有运行中的托管命令时解绑并退出 Root 服务。界面显示“Root 已就绪”，再次操作时按需连接；仅恢复应用前台不会为了维持“已连接”而重建空闲服务。
- 运行时的自动权限准备只针对实际连接状态；“Root 已就绪”保留工具可用性，却不触发新的权限准备和连接。为此补充真实运行时的状态流回归，防止空闲退出被上层自动准备逻辑抵消。
- 托管命令运行期间保持服务；命令有既有的并发、输出和超时限制。只在还有命令运行时延后空闲检查，不在空闲状态周期性启动 Root。
- 关闭 Power 模式或切换接入方式会主动解绑，并取消本服务拥有的命令。普通绑定服务也随客户端进程结束而清理。
- 使用 `setsid -w` 为命令建立独立进程组，并等待真实命令退出。每组附带一个阻塞管道的生命周期监听进程；宿主意外退出时管道 EOF 触发本组清理，不靠轮询唤醒 CPU。
- 正常命令退出后先关闭生命周期管道，再等待输出 EOF，避免监听进程持有管道而把成功命令误报为超时。主动取消和超时都清理进程组、输入输出流和读取任务。

本批不增加后台执行屏、按键映射、持续录音或锁屏自动操作，也不据此宣称已降低实测耗电。长时间熄屏、Doze 与真实功耗仍按后续批次独立验收。

- Debug、AndroidTest 和 Release/R8 构建通过，Debug Lint 为 0 错误。最终构建和静态检查日志为 `build/root-service-idle-regression-build.log`、`build/root-service-idle-regression-lint.log`。
- 真机核心用例 5 项通过，见 `build/root-service-phone-accepted-core.log`；客户端进程退出另有 seed / verify 两阶段均通过，见 `build/root-service-phone-accepted-client-seed.log`、`build/root-service-phone-accepted-client-verify.log`。

| 真机验证 | 结果 |
| --- | --- |
| 真实 Root 服务身份与只读设备状态 | UID 0、PID 与客户端不同；电量、存储、亮度和音量读取通过 |
| 重复操作与空闲退出 | 连续操作复用同一 Root PID，实际等待空闲释放后，再次操作使用新 PID |
| 阻塞的设备调用取消 | 取消仅关闭该请求的进程组，其他请求仍可读取前台应用 |
| 托管命令与主动释放 | 运行中保持服务；取消及主动解绑均清理对应进程组 |
| Root 服务意外退出 | 故障结束服务后，子进程组退出；新操作可重连，旧命令 ID 不会恢复执行 |
| 应用客户端进程结束 | seed 后实际 force-stop 应用，再以冷进程核对旧 Root PID 和命令进程组均已退出，旧命令未重建 |

此外，打开真实“手机操作”设置页，确认空闲后显示“Root 已就绪”，同时进程列表中已无 Root 服务；证据为 `build/root-service-phone-idle-ready.xml` 和对应截图。该联调验证了运行时不会因自动权限准备而重新拉起已释放的服务。系统助手按键也重新验证可唤起原有轻量面板，随后关闭空面板，没有提交模型请求。

测试前后逐项核对：接入方式仍为 Root，Power、命令执行和记忆均保持开启；默认助手仍为 Floryx Dev，原 vivo 语音识别器保持一致。诊断标记已清除，没有遗留任务前台服务。诊断用例使用只读状态和本应用创建的测试进程，不接入用户的聊天运行时或模型服务商；状态流单元测试使用本地假客户端。
