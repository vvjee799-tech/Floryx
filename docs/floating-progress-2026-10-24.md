# 后台悬浮窗执行反馈

## 原因与修改

命令执行期间，聊天记录原本每秒更新耗时，但悬浮窗桥接只提取助手文字和工具名称。文字不变时，桥接状态也不变，展开的面板看起来像停住。

现在悬浮窗独立显示任务状态，使用当前会话、本轮命令的实际运行快照判断“正在执行命令”，并用命令开始时间计时。计时由悬浮窗本地每秒更新，不依赖 stdout 新输出，也不增加模型请求。计时表示已等待的时长，不代表完成百分比，也不能证明命令的业务逻辑正在取得进展。

- 固定状态区区分准备命令、执行命令、执行操作、等待模型、生成回复、等待确认、暂停、停止、中断和本轮结束。
- 长命令显示耗时以及“等待命令返回结果，可随时停止”；旧回复仍在下方可滚动查看。
- 收起时增加运行环，展开后的停止入口增加文字，保留 48dp 触摸高度。
- 确认请求不显示成正在执行；停止时不沿用旧工具的运行状态；工具失败后若本轮成功恢复，不误标整个任务失败。
- 状态计时仅在当前阶段活跃时运行；展开面板的计时以真实开始时间为基准，不以面板打开时间为基准。

## 验证

- 347 项单元测试：346 通过、1 项既有环境限制跳过，0 失败。新增状态映射覆盖静默命令、旧命令、命令结束、等待确认、停止及错误恢复。
- Debug 与 AndroidTest 构建通过，覆盖安装到 MuMu `127.0.0.1:16384`。
- 实际运行 20 秒命令，首段输出后保持静默；后台助手文字不变时，界面耗时继续增加，期间仍只有一次启动模型请求。
- 命令结束后显示“本轮已结束”；第二条长命令通过悬浮窗“停止”取消，实际进程状态为 Cancelled，界面显示“任务已停止”。
- 设备测试入口：`TerminalAgentDiagnosticTest`，参数 `runTerminalDiagnostics=true`、`runOverlayCommandDiagnostics=true`。使用本地模拟模型调度实际 Linux 命令，无外部模型额度消耗。
- 最终 APK 的深、浅色悬浮窗回归均通过：触摸及滑动穿透、操作中控件让开、结束后恢复、重复展开收起、48dp 圆形窗口与前后台切换；截图人工检查通过。

日志：`build/overlay-progress-build.log`、`build/overlay-command-progress.log`、`build/overlay-progress-final-dark.log`、`build/overlay-progress-final-light.log`。截图：`build/overlay-progress-evidence/`。

最终 Debug APK：`app/build/outputs/apk/debug/app-debug.apk`，SHA-256 `5A9CED939EADECA98FC6E7D871B7657AF2382EDE78D041B9E336B6FFB924ED06`。

## 测试过程中发现的问题

连续进行深浅色回归时，专用测试 Activity 保留了上一轮的触摸计数，导致第二轮触摸穿透断言误报。测试启动改成清空该专用 Activity 的任务并重新创建，避免跨轮状态污染；没有清空 Floryx 的数据。

本轮仅更新 MuMu 的 Floryx Dev。手机需安装更新后才会出现此反馈。
